# 찐청소 가독성 기준

## 변경 금지
- 읽기 편하게 만든다는 이유로 문구·조건·제외 항목·FAQ 답변을 삭제하거나 요약하지 않는다.
- 본문을 line-clamp, 고정 높이, overflow hidden으로 잘라내거나 새 아코디언으로 숨기지 않는다.
- 실제 사례와 사진 설명, SEO 제목·메타·구조화 데이터·링크는 디자인 변경과 분리한다.
- PC와 모바일을 함께 검증한다. 배포는 사용자 확인 전 금지한다.

## 재사용 방법

모바일 메뉴 장식: 상단 3개 링크 앞에 작은 V·겹화살표를 배치한다. 접힌 서비스 분류의 화살표 3개는 항상 보이며 0.5초마다 ◁◁◁ → ◁◁◀ → ◁◀◀ → ◀◀◀ → ◁◀◀ → ◁◁◀ 순서로 채움을 바꾼다. 개수나 불투명도를 바꾸는 방식이 아니다. 고정 너비와 모션 감소 설정을 유지한다.

## 화면 기준
- 본문 16~18px, 보조 설명 14px 이상을 기본으로 한다. 작은 숫자·장식 라벨은 별도 판단한다.
- 긴 한글 문장은 단어 단위로 줄바꿈하되 긴 URL 등은 화면을 넘기지 않게 한다.
- 모바일에는 억지로 여러 열을 유지하지 않는다. PC 본문 최대 폭 48rem.
- 목차 링크는 최소 44px 높이. 고정 헤더 아래로 제목이 드러나는지 실제 이동으로 확인한다.
- 목차 메뉴는 박스 없이 텍스트와 장식용 왼쪽 화살표 3개로 표시한다. 모션 감소 설정에서는 움직임을 끈다.
- 목차 내부 스크롤은 사용하지 않는다. PC 높이 1000px 이상에서만 고정하고, 낮은 화면에서는 페이지와 함께 스크롤한다. 새 메뉴를 추가하면 고정 상태에서 마지막 항목까지 화면에 들어오는지 다시 검증한다.
- 이미지 전후 표시·순서·alt를 유지한다. 표는 데이터를 보존하며 재배치한다.
- 최소 320/390/768/1280px에서 가로 넘침, 고정 요소 충돌, 문구 잘림을 확인한다.
- 본문·링크·이미지·SEO의 변경 전후 비교, 프로덕션 빌드, 브라우저 새로고침까지 확인한다.

## 모바일 문장 배치 (공통)
- `ReadingParagraph`는 원문 문자와 공백을 그대로 유지하며 문장 경계에 span만 추가한다.
- 639px 이하에서 문장별로 줄을 바꾸고 문장 사이에 0.75em 여백을 둔다. PC에서는 inline으로 이어진다.
- 긴 문장은 검토한 의미 단위만 `breakAfter`로 지정한다. 글자 수 기준으로 자동 절단하거나 표현을 고쳐 쓰지 않는다.
- "한 문장 한 줄"은 한 화면 줄에 억지로 넣는 뜻이 아니다. 화면 너비에 따른 자연스러운 줄바꿈을 허용한다.
- 숫자·조건·예외·FAQ를 보존하고, 검색용 별도 본문이나 모바일 전용 축약문은 만들지 않는다.

## 검증
지역페이지는 지역명만 치환한 설명을 늘리지 않는다. 안양 예시는 등록된 지역 사진과 공간 유형에 맞는 상담 조건을 연결한다. 일반적인 상담 안내와 실제 현장의 작업 기록을 명확히 구분하며, 인원·시간·금액·작업 방법의 선택 이유는 확인된 기록이 있을 때만 사례로 기재한다. 상세 기록이 부족하면 별도 사례 URL을 생성하지 않는다.
- `node work/service-readability-audit.cjs`: 35개 페이지의 기존 본문·링크·사진·제목·메타·JSON-LD 보존 및 목차 복귀 구조 확인. 3101 로컬 서버가 필요하다.
- 원본 기준 파일을 변경 후 결과로 덮어쓰지 않는다. 새 서비스는 검증 대상 목록에 추가하고, 기존 페이지의 기준은 유지한다.
- `node --test tests/*.test.mjs`와 `npm run build`를 실행한다.
- 화면 폭별 가로 넘침 검사와 별도로 실제 스크린샷, 메뉴 이동, 복귀 및 헤더 가림을 확인한다.

## 2026-09-26 사용자 승인 디자인·가독성 기준 (원문)

### 1. 콘텐츠 보존 — 최우선 원칙
- 기존 문장·단어·숫자·조건·예외·주의사항·FAQ 답변을 삭제하거나 축약하지 말 것.
- 가독성을 이유로 표현을 다시 쓰거나 의미를 바꾸지 말 것.

- 새로운 사실, 수치, 효과, 사례를 임의로 추가하지 말 것.

### 2. 모바일 — 문장 단위와 짧은 호흡으로 배치
- 여러 문장이 붙은 문단은 문장 끝에서 줄을 나누고 적절한 여백을 줄 것.
- 긴 문장은 의미가 자연스럽게 이어지는 지점을 검토하여 추가로 줄바꿈할 것.
- 단순히 글자 수에 맞춰 일괄로 자르지 말 것.
- '한 문장 한 줄'은 한 문장을 화면 한 줄에 억지로 넣으라는 뜻이 아니다.
- 화면 너비에 따른 자연스러운 줄바꿈을 허용하고, 줄 수를 맞추려고 글씨를 작게 만들지 말 것.
- 숫자와 단위, 밀접한 단어 묶음이 어색하게 분리되지 않도록 확인할 것.
- 짧은 의미 묶음 사이에는 눈이 쉴 수 있는 여백을 주되, 줄마다 과도한 공백을 넣지 말 것.
- 원문은 그대로 두고 줄바꿈·여백·글자 배치만 조정할 것.

### 3. PC — 자연스러운 문장 흐름 유지
- 모바일용 강제 줄바꿈을 PC에 그대로 적용하지 말 것.
- PC에서는 문장이 자연스럽게 이어지도록 할 것.
- 본문 폭을 제한하여 한 줄이 지나치게 길어지지 않도록 할 것.
- 제목·본문·보조 설명의 크기와 굵기를 구분할 것.
- 제목 앞에는 충분한 여백을 주고, 서로 이어지는 문단은 과하게 떨어뜨리지 말 것.
- 태블릿에서도 본문이 지나치게 좁아지지 않도록 할 것.

### 4. 시각적 정보 구분

- 색상에만 의존하지 말고 제목·테두리·배경·간격을 함께 활용할 것.
- 모든 문장을 굵게 표시하거나 모든 내용을 카드로 감싸지 말 것.
- 핵심 조건과 예외 사항이 장식이나 작은 글씨에 묻히지 않도록 할 것.
- 새로운 요약문이나 접기 기능으로 기존 본문을 대체하지 말 것.

### 5. 페이지 내 목차

- 모바일·태블릿·PC 화면에서 실제로 확인할 것. 예시 너비: 320px, 390px, 768px, 1280px.

- 완료 후 변경 사항, 원문 보존 검증 결과, 남은 문제와 미리보기 방법을 알려줄 것.

- 사용자 승인 없이 배포·게시·커밋·푸시하지 말 것.

## 2026-09-26 지역-서비스 글 작성 기준 (원문)

이 목록은 `/{서비스}/{지역}/` 형태 지역-서비스 페이지(`src/lib/regional-pages.json`, `docs/landing-workflow.md` 참고)를 새로 작성하거나 갱신할 때 위 디자인·가독성 기준과 함께 적용한다.

1. 지역명만 바꾼 복제형 페이지를 만들지 말 것.
2. 사용자가 제공한 실제 현장 정보와 사진만 작업 사례로 사용할 것.
3. 확인되지 않은 재질, 오염, 작업 방법, 가격, 인원, 시간은 만들지 말 것.
4. 정보가 부족하면 임의로 작성하지 말고 필요한 내용을 먼저 질문할 것.
5. 실제 작업 사례와 일반적인 상담 안내를 명확하게 구분할 것.
6. 고객이 가장 궁금해하는 작업 범위, 견적 기준, 별도 항목, 진행 순서를 결론부터 설명할 것.
7. 중요한 내용을 가독성을 이유로 삭제하거나 축약하거나 의미를 바꾸지 말 것.
8. 모바일과 PC에 동일한 핵심 내용을 제공하고 배치와 글자 크기만 반응형으로 조절할 것.
9. 문장은 한 문장 한 호흡을 기준으로 의미 단위에서 줄을 나눌 것.
10. 부자연스러운 SEO 문장과 키워드 반복을 제거할 것.
11. 찐청소의 정직하고 전문적인 말투를 사용하되, 서비스 성격에 맞는 가벼운 유머만 허용할 것.
12. 고객이 검색하는 지역+서비스, 가격, 비용, 견적, 업체, 공간, 재질, 오염 증상을 자연스럽게 반영할 것.
13. 평수만으로 가격을 단정하지 말고 실제 작업량, 인원, 장비·약품, 기존 상태, 집기와 동선을 반영할 것.
14. 작업 전후 사진에는 장소, 재질, 오염, 작업 방법, 인원·시간, 어려웠던 조건, 결과와 한계를 설명할 것.
15. 동일한 지역의 사례라도 다른 현장과 같은 가격·시간·결과를 보장하지 않는다고 안내할 것.
16. 실제 지역 사진이 아닌 참고 사진을 사용한다면 해당 지역 사진이 아니라고 명확하게 표시할 것.
17. FAQ는 실제 고객 질문 형태로 작성하고 답을 먼저 제시할 것.
18. 화면에 보이는 FAQ와 FAQ 구조화 데이터의 문답을 동일하게 유지할 것.
19. Service, BreadcrumbList, FAQPage 구조화 데이터와 canonical, 메타 제목, 메타 설명을 구성할 것.
20. 실제 사례, 상위 서비스, 관련 서비스, 견적 문의로 자연스럽게 내부 링크를 연결할 것.
21. 모든 링크와 목차, 상단 이동 버튼이 PC와 모바일에서 정상 작동하는지 확인할 것.
22. 기존 페이지와 내용이 불필요하게 중복되면 제거하되, 필요한 작업 정보는 보존할 것.
23. 완성 후 빌드, 모바일·PC 화면, 구조화 데이터, 링크, 사이트맵 포함 여부를 검사할 것.
